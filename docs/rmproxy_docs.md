# rmproxy

Обратный прокси-сервер с поддержкой мандатного управления доступом (MAC)
для Astra Linux Special Edition.

`rmproxy` принимает входящие HTTPS-запросы, аутентифицирует пользователя
по Kerberos (SPNEGO/Negotiate), сравнивает мандатные метки пользователя,
его рабочей станции и целевого ресурса средствами PARSEC, и при
положительном решении прозрачно проксирует запрос на бэкенд. Решение
о допуске принимается до того, как трафик попадёт в приложение, что
позволяет встраивать мандатное разграничение без модификации самих
веб-сервисов.

## Возможности

- Терминирование TLS 1.2+ с принудительным запретом ренеготиации
  и серверными приоритетами шифров
- Прозрачная Kerberos-аутентификация по схеме HTTP Negotiate (SPNEGO),
  совместимая со стандартными браузерами и `curl --negotiate`
- Получение мандатных меток пользователя из локального кэша SSSD
  через D-Bus (InfoPipe)
- Получение мандатных меток узлов из FreeIPA по LDAP с привязкой
  через SASL/GSSAPI
- Сравнение меток через штатный API PARSEC (`libpdp`)
- Установка мандатной метки на дочерний процесс прокси перед
  обращением к бэкенду (`mac_set_pid`)
- Модель «fork на соединение» — изоляция клиентов на уровне процессов
- Подготовленная инфраструктура для подписи JWT (HMAC-SHA256)
  с секретом, выносимым в конфигурацию

## Архитектура

```
                      ┌────────────────────┐
                      │       KDC          │
                      │   (Kerberos 5)     │
                      └─────────┬──────────┘
                                │  тикеты
                                │
┌──────────┐    HTTPS    ┌──────┴───────┐    TCP    ┌──────────┐
│ Клиент   │────────────►│   rmproxy    │──────────►│ Бэкенд   │
│ (Astra)  │  SPNEGO     │              │           │          │
└──────────┘             └──┬───────┬───┘           └──────────┘
                            │       │
                       LDAP │       │ D-Bus
                            │       │
                  ┌─────────▼──┐  ┌─▼────────┐
                  │  FreeIPA   │  │   SSSD   │
                  │ (каталог)  │  │  (кэш)   │
                  └────────────┘  └──────────┘
```

Прокси выступает посредником между клиентом и веб-приложением. Все
проверки выполняются до открытия соединения с бэкендом. Сам бэкенд
о наличии мандатной модели может ничего не знать.

---

## Поток обработки запроса

1. Главный процесс слушает TCP-порт из `mrp.conf` и принимает входящие
   соединения.
2. На каждое соединение делается `fork()`. Дочерний процесс выполняет
   TLS-handshake средствами OpenSSL.
3. Запускается цикл SPNEGO:
   - читается HTTP-заголовок;
   - извлекается поле `Authorization: Negotiate <base64>`;
   - вызов `gss_accept_sec_context()` валидирует Kerberos-тикет;
   - при необходимости отдаётся `401` с продолжением SPNEGO;
   - на успехе из контекста извлекается UPN пользователя
     (например, `user@DOMAIN.NET`);
   - первичный HTTP-запрос целиком сохраняется во внутренний буфер,
     чтобы потом без потерь дослать его на бэкенд.
4. Получаются три мандатные метки:
   - метка пользователя — из SSSD через D-Bus (атрибут
     `x-ald-user-mac`);
   - метка рабочей станции пользователя — из LDAP по FQDN клиента
     (атрибут `x-ald-host-mac`);
   - метка целевого ресурса — из LDAP по FQDN бэкенда.
5. Метки преобразуются в объекты `mac_t` через `mac_from_text()`
   и сравниваются через `mac_cmp()`.
6. При положительном решении:
   - метка пользователя устанавливается на текущий процесс прокси
     через `mac_set_pid()`;
   - открывается TCP-соединение к бэкенду;
   - в него отправляется сохранённый первичный запрос;
   - запускается двунаправленный обмен через `poll()`.
7. При отрицательном решении соединение закрывается.

## Зависимости

Все пакеты доступны в репозиториях Astra Linux SE:

- `libsystemd-dev` — sd-bus для общения с SSSD InfoPipe
- `parsec-dev` — заголовки и библиотеки PARSEC (`libpdp`)
- `libkrb5-dev` — GSSAPI и Kerberos 5
- `libldap-dev` — клиент OpenLDAP
- `libssl-dev` — OpenSSL для TLS и базовых криптопримитивов

## Сборка

```bash
gcc proxy.c sssd.c config.c http.c -o proxy -lpdp -lgssapi_krb5 -lcrypto -lsystemd -lldap -lssl
```

В результате в текущем каталоге появляется исполняемый файл `proxy`.

## Конфигурация

Файл `mrp.conf` в рабочем каталоге запуска:

```
port        = 8888
t_port      = 8000
t_addr      = 0.0.0.0
dc_url      = astraipa.domain.net
cert_path   = ./cert/
jwt_secret  = rmproxysecret
```

Поля:

| Параметр     | Назначение                                                |
|--------------|-----------------------------------------------------------|
| `port`       | TCP-порт, на котором прокси принимает TLS-соединения      |
| `t_port`     | Порт бэкенда                                              |
| `t_addr`     | IP-адрес бэкенда                                          |
| `dc_url`     | FQDN сервера FreeIPA (используется для LDAP-запросов)     |
| `cert_path`  | Каталог с TLS-сертификатом и закрытым ключом              |
| `jwt_secret` | Секрет HMAC для подписи JWT                               |

> **Внимание.** Значение `jwt_secret` должно быть длинным и уникальным
> в продуктивной установке. Значение из шаблона приведено
> исключительно для отладки.

TLS-сертификат и ключ ожидаются по путям `cert_path/cert.pem`
и `cert_path/key.pem`. Самоподписанный комплект для теста:

```bash
mkdir -p cert
openssl req -x509 -newkey rsa:4096 \
    -keyout cert/key.pem -out cert/cert.pem \
    -sha256 -days 3650 -nodes \
    -subj "/C=XX/ST=State/L=City/O=Company/OU=Section/CN=localhost"
```

## Настройка инфраструктуры

### 1. Расширение схемы LDAP

Скопировать файл схемы в каталог 389 Directory Server:

```bash
sudo cp 74x-ald-host-mac.ldif /etc/dirsrv/slapd-*/schema/
sudo chmod 660 /etc/dirsrv/slapd-*/schema/74x-ald-host-mac.ldif
```

Перезапустить службы каталога и SSSD:

```bash
sudo systemctl restart dirsrv@<INSTANCE>.service
sudo systemctl restart sssd
```

Имя инстанса `dirsrv@...` можно посмотреть командой:

```bash
ls /etc/systemd/system/ | grep dirsrv
```

### 2. Атрибуты SSSD

В `/etc/sssd/sssd.conf` в разделе `[domain/<your.domain>]`:

```
ldap_user_extra_attrs = x-ald-user-mac
```

В разделе `[ifp]`:

```
user_attributes = +x-ald-user-mac
```

### 3. Назначение меток узлам в FreeIPA

```bash
ipa host-mod astraipa.domain.net \
    --addattr=objectClass=x-ald-host-parsec

ipa host-mod astraipa.domain.net \
    --addattr=x-ald-host-mac="2:0x2:2:0x2"
```

Для последующего изменения метки использовать `--setattr`
вместо `--addattr`.

### 4. Право чтения метки узла

```bash
ipa permission-add "Read host mac" \
    --type=host \
    --right={read,compare,search} \
    --attrs=x-ald-host-mac \
    --bindtype=all
```

### 5. HTTP keytab

Сервису, под которым работает прокси, должно быть разрешено
использование HTTP keytab. В веб-интерфейсе FreeIPA:
**Identity → Services → HTTP → Allow to retrieve keytab**.

## Запуск

С повышенными PARSEC-привилегиями через `execaps`:

```bash
sudo execaps -c 0x00004 \
    env KRB5_KTNAME=/var/lib/ipa/gssproxy/http.keytab ./proxy
```

Альтернативный вариант — выдать пользователю, под которым запускается
прокси, постоянные привилегии PARSEC и запускать без `execaps`.

После старта в stdout появится строка:

```
Listening on port 8888
```

Проверочный запрос с клиентской машины с актуальным Kerberos-тикетом:

```bash
curl --negotiate -u : -k https://<proxy-host>:8888/
```

## Логика принятия решения

Метка имеет формат:

```
<lvl_min>:<cat_min>:<lvl_max>:<cat_max>
```

Например: `2:0x2:2:0x2`. Для сравнения используется минимальная часть
(`lvl_min`, `cat_min`).

Прокси последовательно выполняет две проверки.

### Проверка 1. Согласованность сессии входа

Метка пользователя должна совпадать с меткой его рабочей станции.
Это защищает от попыток повысить уровень относительно того, с которым
пользователь зашёл в систему. При несовпадении соединение
закрывается.

### Проверка 2. Доминирование над меткой ресурса

Сравнивается метка пользователя с меткой целевого узла-ресурса
через `mac_cmp()`:

| Результат `mac_cmp` | Интерпретация                        | Действие                              |
|---------------------|--------------------------------------|---------------------------------------|
| `-2`                | Метки несравнимы                     | Отказ                                 |
| `-1`                | Пользователь ниже ресурса            | Отказ                                 |
| `0`                 | Метки равны                          | `mac_set_pid()` и проксирование       |
| `1`                 | Пользователь доминирует над ресурсом | Проксирование                         |

Поведение соответствует классической модели Белла–Лападулы в части
запрета «чтения вверх».

## Ограничения и направления развития

- **Метки берутся только по первичной паре (пользователь, бэкенд).**
  После успешной проверки соединение бриджуется на уровне TCP, и
  последующие HTTP-запросы по тому же keep-alive-каналу не
  переоцениваются. Для разграничения по URI требуется
  HTTP-aware-режим пересылки.
- **Запрос метки узла через LDAP заметно дороже обращения к SSSD.**
  В коде присутствует заготовка JWT (`http.c::create_jwt`)
  с конфигурируемым `jwt_secret` — она задумана как основа для
  кэширования метки узла на стороне клиента/сессии.
- **Только IPv4 в текущей версии** (`AF_INET` в `socket()`/`bind()`).
- **Журналирование сейчас идёт в stdout.** Для эксплуатации полезно
  перевести вывод в `systemd-journal` или syslog.
- **Поддержка HTTP/2 и WebSocket** в текущей реализации не
  предусмотрена.
